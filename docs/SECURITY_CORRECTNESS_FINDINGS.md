# Security & Correctness Findings — OTS_WebEditor

**Date:** 2026-07-02
**Scope:** `app/api/**` routes, `lib/**` services, score-loading/render path in `components/ScoreEditor.tsx`, `next.config.ts`, and a spot-check of `webmscore-fork/web/main.cpp`. Found while surveying the codebase for the feature-parity roadmap (`docs/MUSESCORE_FEATURE_PARITY_ROADMAP.md`). Severities assume a public (internet-reachable) deployment of the non-embed Next.js app; several items are non-issues if the API is deployed only behind an authenticated gateway.

---

## High

### H1. Unauthenticated routes spend server-side LLM API keys
`lib/music-agents/router.ts:1198–1204` and `lib/music-services/patch-service.ts:70–85` fall back to `process.env.ANTHROPIC_API_KEY` / `OPENAI_API_KEY` / `GROK_API_KEY` / `DEEPSEEK_API_KEY` / `KIMI_API_KEY` when the request supplies no key. The routes that reach this code (`/api/music/agent`, patch/generate flows; also `HF_TOKEN` fallback in `app/api/music/generate/stream/route.ts:124` and the Hugging Face space tokens in the OMR/notagen services) perform **no authentication, authorization, or rate limiting**. Anyone who can reach the deployment can drain the deployment's paid API credits, use it as a free LLM relay, and (for prompt-bearing routes) exfiltrate whatever context the server augments (e.g. source-RAG content).

**Recommendation:** require an app-level auth token (or session) on every route that can consume a server-side credential; add per-IP rate limiting; consider making env-key fallback opt-in via an explicit `ALLOW_SERVER_LLM_KEYS=1` so self-hosters don't expose it by accident.

### H2. LLM proxy endpoints are an open relay for arbitrary keys
`app/api/llm/{openai,grok,deepseek,kimi,anthropic,gemini}/route.ts` (shared logic in `app/api/llm/openai-compatible.ts:210`) accept an `apiKey` in the POST body and forward requests server-side with no auth or rate limiting. Even without server keys this makes the deployment a generic proxy (abuse/ban risk, provider ToS exposure, and your server sees users' secret keys in plaintext request bodies). Upstream provider error bodies are also returned verbatim (`openai-compatible.ts:295–320`), which can leak deployment configuration details.

**Recommendation:** same auth/rate-limit gate as H1; never log request bodies on these routes (current `logApiRouteSummary` is metadata-only — keep it that way); consider moving user-key calls fully client-side where providers' CORS allows it, so keys never transit the server.

## Medium

### M1. `/api/fetch-score` proxy: redirect-following SSRF surface and unbounded response buffering
`app/api/fetch-score/route.ts` validates only the *initial* URL against the Google Drive allowlist, then fetches with `redirect: 'follow'` (line 29–32). A redirect chain from the allowlisted host is followed to **any** destination (including internal/metadata addresses), and the response is fully buffered with `await upstream.arrayBuffer()` (line 44) with **no size cap and no timeout** — a link to a multi-GB Drive file (or a slow-loris upstream) can exhaust server memory or hold connections open.

**Recommendation:** use `redirect: 'manual'` and re-validate each hop against the allowlist (or at minimum block non-https and private/link-local IP literals); enforce a response size limit (stream + count bytes, abort past e.g. 100 MB) and an `AbortSignal.timeout(...)`; restrict the returned `Content-Type` to expected score/XML/zip types.

### M2. ScoreOps session store grows without bound
`lib/music-services/scoreops-session-store.ts` keeps sessions in a module/global `Map` with **no TTL, no eviction, and no size limit**; each session stores the full score `content` string. Unauthenticated calls to `/api/music/scoreops/session/open` can grow server memory indefinitely (DoS). Correctness: the store is per-process, so sessions silently vanish on restart and don't work behind multi-instance deployments.

**Recommendation:** add max-entry + TTL eviction (the artifact store in `lib/score-artifacts.ts` already implements exactly this pattern — TTL + periodic cleanup — reuse it); cap accepted content size; document the single-instance constraint or back the store with the artifact dir.

### M3. No security headers / CSP; engine SVG injected via `innerHTML`
`next.config.ts` sets only cache headers; there is no CSP, `X-Content-Type-Options`, or `Referrer-Policy`. Rendered SVG is injected with `containerRef.current.innerHTML = svgData` (`components/ScoreEditor.tsx:5794,5851`). The SVG is generated by the WASM engine (Qt SVG writer escapes text), so this is not directly exploitable today, but the input to that engine is **arbitrary attacker-supplied XML** in compare/embed mode (`?compareLeft=`/`?compareRight=` fetch any URL, `ScoreEditor.tsx:2178`) and `?score=` loads any URL — a single escaping bug anywhere in the engine's text→SVG path becomes stored XSS.

**Recommendation:** add a CSP (`script-src 'self' 'wasm-unsafe-eval'`, no inline script) and standard hardening headers for the non-embed build; optionally sanitize engine SVG output (e.g. strip `<script>`, `<foreignObject>`, `on*=` attributes) before injection as defense-in-depth; for hosted embed deployments consider an origin allowlist for `compareLeft/compareRight/score` URLs to prevent the editor being used to render/phish arbitrary third-party content.

### M4. User LLM API keys persisted in `localStorage`
`components/ScoreEditor.tsx:1915–1929` caches the user-entered AI API key in `localStorage`. Combined with M3 (no CSP), any XSS anywhere on the origin exfiltrates provider keys. `localStorage` also persists indefinitely on shared machines.

**Recommendation:** prefer `sessionStorage` (or in-memory with explicit "remember" opt-in); ship the CSP from M3.

## Low / Correctness

### L1. Newer-format score data silently dropped on load (data-loss risk on round-trip)
`MSCVERSION` is still `400` (`webmscore-fork/src/engraving/libmscore/mscore.h:32`) while `loadMsczOrMscx(..., ignoreVersionError=true)` (`web/main.cpp:324`) lets 4.1–4.7 files through a reader that skips unknown tags. Loading a 4.7 file and saving from the web editor **silently loses** any element the 4.00 reader doesn't understand. `<harmonyInfo>` is now handled (`harmony.cpp:358`), but the rest of the 4.1–4.7 delta is not. Tracked as roadmap P2 — flagged here because it is user-visible data loss, not just missing rendering. Consider a load-time warning banner ("saved by a newer MuseScore; some elements may be dropped") until parity.

### L2. Debug artifacts in production paths
- `printf("[WASM SELECT] ...")` on every selection (`web/main.cpp:2542`) — noisy and a (tiny) perf hit per click.
- `exposeScoreToWindow` (`components/ScoreEditor.tsx:4321`) attaches the live score handle to `window` unconditionally — handy for debugging, but widens the XSS blast radius (M3/M4) and should be dev-gated.

### L3. Embed builds skip type checking
`next.config.ts:11–13`: `typescript.ignoreBuildErrors` is `true` whenever `BUILD_MODE === 'embed'`, so type errors can ship in embed releases unless `npm run typecheck` is run separately. Make the separate typecheck a required CI step for embed builds.

### L4. Format sniffing scans entire file, byte-by-byte, in JS
`detectScoreInputFormat` → `containsAscii` (`lib/public-score-url.ts:56–76`) does an O(n·m) linear scan over the **whole** uploaded buffer (potentially tens of MB for MSCZ with embedded audio) on the main thread, twice in the worst case (`.mscx` probe then `container.xml` probe). ZIP central-directory entries live at the end of the file; scanning the last ~64 KB is sufficient. Also, an MXL whose internal filenames merely contain the substring `.mscx` would be misdetected as MSCZ.

### L5. `handleScorePointerUp` uses stale pointer coordinates edge case
Minor: in `components/ScoreEditor.tsx:12423`, if `clientToScorePoint` fails at pointer-up (e.g. release outside the container), the drag rect state is cleared but no selection refresh runs — selection UI can briefly desync from WASM state. Cosmetic; worth folding into the pointer-state rework planned for drag editing (roadmap §2.1).

### L6. Trace headers are attacker-controllable and forwarded upstream
`lib/trace-http.ts` derives trace/session IDs from inbound request headers and `withTraceHeaders` forwards them to third-party APIs (`openai-compatible.ts:283`). Not directly dangerous, but log-correlation values should be validated (length/charset) before being trusted in logs or echoed upstream, to prevent log-injection/spoofed correlation.
